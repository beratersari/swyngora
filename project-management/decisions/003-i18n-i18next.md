# 003 — Client localization with i18next

| Field | Value |
|---|---|
| **Status** | accepted |
| **Date** | 2026-07-26 |
| **Package** | `frontend/` |

## Context

Product UI had English hard-coded across pages and organisms. Need flexible multi-language support without a second ad-hoc string system.

## Decision

Use **i18next** + **react-i18next** + browser language detector:

- Catalogs: `src/libs/i18n/locales/<lng>/{common,markets,detail}.json`
- Default / fallback: `en`
- First extra locale: `tr`
- Header **LanguageSwitcher**; persist via `localStorage` (`swyngora.locale`)
- Ant Design `ConfigProvider.locale` synced from app language

## Rules

1. No user-visible English (or other) hard-coded in components — use `t('ns:key')`.
2. Domain identifiers (exchange ids, symbols, intervals) stay untranslated.
3. Add languages by registering locale JSON + `SUPPORTED_LOCALES` + optional Ant Design pack.

## Alternatives rejected

- Hand-rolled `dict[lang][key]` — less tooling, plurals, and detector support.
- Loading catalogs only from CDN — overkill for v1; can add `i18next-http-backend` later.
